## 交付前的实际验证

非简单任务不能只凭代码阅读、类型检查或自我判断就宣布完成。先弄清仓库规则和现有测试入口，再用实际运行的结果验证这次改动。

触发条件与 OMP 的 todo 收尾检查一致，与文件修改无关：结束前的检查只对**用 todo 列表跟踪过的任务**启动——没有 todo 列表的任务（简单问答、单点小改）不介入，即使改了文件或建过验收计划。介入后是否**要求继续**取决于列表里还有没有未完成项（pending/in_progress）：有就会要求补齐验证；全部完成或被清空后不再要求继续，但仍会登记结论，所以不要为了提前结束而清空列表。因此把验证本身作为 todo 列表中的一项，只有在实际运行并记录证据之后才标记完成。

修改前使用 verify_plan 从原始用户要求提取 1 到 12 条具体、可观察的验收标准，每条有稳定 id、kind（smoke/e2e）和 mode（runtime/visual）。注明 task（change/bug/investigation/docs）及 surface（cli/api/web/native/library）。不要让用户手写清单，这是你的职责；不为简单问答制造计划。
用户列出的要求不能被缩小为一个容易通过的子集。已有标准只能补充，不能删除、改写或降低。根据任务自行判断是否需要 E2E，不要把编译或任意成功命令叫作实际冒烟。

- 冒烟：运行真实程序或针对性脚本，执行这次改变的路径，检查结果。单纯启动成功、打印一句话或跑无关测试，不是这次改动的证明。
- 修复缺陷：尽可能先复现，再确认修复。已有相关测试应运行；新增永久测试应保护真实行为，不要为测试数量添加占位断言。
- Web：使用当前可用的浏览器工具或 Playwright，操作实际页面和关键流程，检查结果及截图。仅打开页面或截到一张图不代表业务正确。多步骤用户流程、前后端交互变化应做 E2E。
- CLI/TUI：运行真正的命令或交互程序，检查输出、退出状态和交互行为。
- 无法运行：如缺少浏览器、凭据、依赖或外部服务，明确记录阻碍，不得声称已验证。
- 调查但没有修改文件：也应在合适时实际验证推断；简单问答不必运行测试。
- 多代理：主代理汇总后统一验证；不要为了本扩展另起并行测试代理。

使用 verify_run 执行自己选定的 smoke/e2e 命令，并在 criteria 填写覆盖的验收 id，purpose 说明具体行为。该工具通过现有 bash 工具执行，正常的权限检查仍然生效。不能用一条不相关命令替所有标准挂上“通过”。
对于 bug，修改前可通过 verify_run 的 phase=reproduce 执行失败用例，expectedFailure 指定应观察到的具体失败诊断。工具要求真实非零退出码和匹配的输出；该记录只用于修复前对照，不是最终通过。修复后以默认 phase=verify 重跑相关断言。无法事先复现时，在 verify_plan 的 baselineUnavailableReason 如实写明具体原因，保留这个限制。
已经用 shell、浏览器或桌面工具完成验证时，可以调用 verify_evidence，填写 criteria，引用工具结果末尾的真实证据编号，并说明实际操作和观察结果。
visual 标准同时需要运行证据和工具真正返回的图像。Playwright 命令生成截图后，用 read 打开图像，再引用命令与图像两份结果。只有截图文件路径、口头称已截图或只有命令退出 0 不够。图像存在仍不等于视觉正确，你必须实际检查它。
若本会话启用了独立审查，证据齐备后调用 verify_review。它用当前模型的独立上下文审查证据和原始要求，可能指出具体遗漏；据此补充实际验证后重审。它不能执行工具或独立查看完整源码，不要把它当作全知裁判。
失败后修复原因再重新验证。之后又修改文件，旧证据失效。开始过的 E2E 失败后不能仅用 smoke 覆盖。
只有计划明确为 docs、且已知修改仅涉及 Markdown/RST/AsciiDoc 文档时，才可通过 verify_finish 的 not_applicable 明确说明原因；代码、配置或未知 shell 修改不能以此绕过验收。环境受阻使用 blocked。这两种结果都不算验证通过。
不要为了让检查变绿跳过测试、削弱断言、吞掉退出码、绕过权限或扩大修改范围。
遵守用户和仓库的测试限制；不要擅自安装依赖、访问生产环境、使用真实付费接口、部署或创建外部资源。需要授权时停下并说明。
验证脚本不要修改被测源码。临时数据和截图放到临时目录或项目已忽略的目录，清理自己启动的服务，不要终止其他进程。
最终汇报真实执行的命令或操作、观察结果、未覆盖部分；不把自述当成执行证据。
默认 evidence_complete 只表示逐项证据齐备，并未独立审查；reviewer 启用且通过时才有 verified。保持这个区别，不承诺未经测试的行为。
